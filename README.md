# Amnezia + FortiClient EMS на одном Mac: диагноз и рабочая схема

Дата: 2026-07-17. Машина: MacBook Pro M4 Max, macOS.
Клиенты: AmneziaWG (сервер amster) + FortiClient EMS (шлюз `sslvpn.2gis.one` = 91.221.199.251).

## TL;DR — порядок запуска

1. Подключить **Amnezia** (AmneziaWG).
2. Запустить `./vpn-on.sh`. Он сам:
   - выведет шлюзы 2GIS (91.221.198/23) из-под туннеля Amnezia;
   - попросит нажать Connect в FortiClient (MFA-пуш придёт как обычно);
   - проверит gitlab и, если сессия «плохая», сам отключит Forti и попросит
     нажать Connect ещё раз (рероллер) — до рабочей сессии;
   - вернёт Telegram-подсети и Claude в туннель Amnezia;
   - прогонит финальные проверки.
3. Перезапустить Claude Desktop (Cmd+Q), если был открыт.

Откат ручных маршрутов и /etc/hosts: `./vpn-off.sh`.

## Что было сломано (три независимые проблемы)

### 1. «Лотерея» доступа к gitlab — проблема на стороне шлюза

Симптом: после коннекта Forti часть корп-ресурсов (gitlab.2gis.ru =
10.251.0.161) случайно оказывается недоступна, при этом planeta.2gis.ru
работает всегда. Помогает только переподключение (иногда 5–10 раз).

Установлено экспериментально:

- Состояние бинарное **per-сессия VPN**: внутри одной сессии стабильно,
  меняется только при реконнекте.
- **Не** зависит от выданного туннельного IP (один и тот же IP встречался и
  в рабочих, и в нерабочих сессиях).
- **Не** зависит от клиента/TLS-стека: в плохой сессии RST получают браузер,
  curl (TLS 1.2 и 1.3), python — все.
- В плохой сессии: ICMP до gitlab ходит, TCP/80 отвечает (403 от сервера),
  **любой TLS на 443 рвётся RST**. Traceroute умирает после первого хопа.
- В хорошей сессии traceroute показывает ECMP-пары (10.54.240.168/.170,
  .165/.167) — за шлюзом несколько путей/узлов.
- EMS к клиенту не привязан (EMS_ADDRESS пуст), ZTNA-правила пустые — 
  posture-теги ни при чём.

Вывод: рассинхрон политики между членами кластера FortiGate или ECMP-путями
за шлюзом. С клиента не лечится — только рероллить сессию (см. vpn-on.sh)
и/или нести админам тикет (готовый текст внизу).

### 2. Forti отваливался при включённой Amnezia

Симптом: при живой Amnezia Forti подключается и через ~250 мс падает
(в vpn-provider.log: `TLS tunnel ... FAILED (Connection reset by peer)`).

Причина (подтверждена tcpdump): AmneziaWG вешает маршруты `0.0.0.0/1` +
`128.0.0.0/1`, которые специфичнее default. GUI-агент Forti авторизуется
через en0, а **сам туннель (network extension) ходит к шлюзу через туннель
Amnezia** — для FortiGate коннект приходит с IP зарубежного VPN-сервера,
и он его режет. Обычный статический /32-маршрут NE-расширению не помогает.

Фикс: маршруты **специфичнее амнезиевских половинок** на подсеть шлюзов:
`91.221.198.0/24` и `91.221.199.0/24` через локальный роутер (en0). Править
конфиг Amnezia не нужно (GUI всё равно не даёт редактировать AllowedIPs).

### 3. Forti перехватывает Telegram и ломает DNS для Claude

Из логов vpn-provider.log: шлюз теперь пушит в туннель Forti не только
10.0.0.0/8, но и **подсети Telegram** (149.154.160/20, 91.108.x/22,
95.161.64/20, 91.105.192/23) и ряд внешних IP. Корп-DNS (10.54.68.68)
становится системным резолвером.

Фикс (как в старом vpn-on.sh, расширен): после коннекта Forti перебить
telegram-подсети на интерфейс Amnezia; IP api.anthropic.com/claude.ai
резолвить через 1.1.1.1 и прибить в /etc/hosts + точечный маршрут в Amnezia.

## Известные хвосты

- **[решено] curl к api.anthropic.com лез на `[::1]:443`**: строка
  `::1 localhost` в /etc/hosts не заканчивалась переводом строки, и `tee -a`
  приклеил запись claude-direct к ней — api.anthropic.com стал алиасом `::1`,
  а IPv4-резолв для имени вообще пропал (hosts перекрывает DNS). Симптомы:
  `Trying [::1]:443` у curl, `curl -4` мгновенно падает с 000. Лечение:
  удалить склеенную строку, вернуть `::1 localhost`, добавить финальный
  перевод строки. vpn-on.sh теперь гарантирует `\n` в конце файла перед
  дозаписью. Тот же баг дремал и в старой версии vpn-on.sh.
- Номера utun-интерфейсов **плавают** (utun4/5/7 — это один и тот же софт в
  разные моменты). Ничего не хардкодить, определять динамически:
  Amnezia = интерфейс с адресом `10.8.*`.
- pf-таблица `<vpnhosts>` от Forti (kill switch) в наших замерах была пуста,
  но правило `block drop out ... to <vpnhosts>` живёт постоянно — если что-то
  внезапно перестанет ходить, первым делом смотреть `pfctl -t vpnhosts -T show`.

## Тикет для админов (черновик)

> SSL VPN sslvpn.2gis.one (91.221.199.251): после переподключения сессия
> случайным образом попадает в состояние, где TCP/443 к gitlab.2gis.ru
> (10.251.0.161) получает RST на TLS ClientHello — любым клиентом (браузер,
> curl, python; TLS 1.2 и 1.3). При этом ICMP и TCP/80 к тому же хосту
> работают, planeta.2gis.ru (10.251.0.131) доступна всегда. Состояние
> стабильно в рамках сессии и не зависит от выданного туннельного IP
> (проверено: один IP давал оба исхода). В рабочих сессиях traceroute
> показывает ECMP-пары 10.54.240.168/.170 и .165/.167. Похоже на рассинхрон
> firewall-политики между членами кластера FortiGate / ECMP-путями.
> Воспроизводится с вероятностью ~30-50% на реконнект.

## Файлы

- `vpn-on.sh` — основной сценарий (замена старого): маршруты для шлюзов,
  рероллер Forti, пост-настройка Telegram/Claude, проверки.
- `vpn-off.sh` — откат ручных маршрутов и /etc/hosts.

## Полезные команды диагностики

```bash
# кто есть кто среди туннелей
ifconfig | grep -A1 "^utun" | grep -B1 "inet "

# куда идёт конкретный адрес
route -n get 10.251.0.161 | grep -E "interface|gateway"

# статус Forti из CLI (UUID может отличаться — см. scutil --nc list)
scutil --nc list | grep -i forti

# мгновенно оборвать Forti (для реролла)
scutil --nc stop <UUID>

# логи Forti
sudo tail -f "/Library/Application Support/Fortinet/FortiClient/logs/vpn-provider.log"
```
